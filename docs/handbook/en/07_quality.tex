\chapter{Test strategy}\label{ch:test-strategy}

Plugins can be tested to a surprising extent without a database. Model building, type
mappings, SQL translation, migration SQL and snapshots only need a connection string, no
connection. The sample's test strategy has four levels:

\begin{datatable}{H{0.78}H{1.70}H{0.52}}
  \textbf{Level} & \textbf{Checks} & \textbf{Database} \\
  \tablehead
  Model tests & Annotations, conventions, validation, options, caching & no \\
  \tablerule
  SQL tests & Translations via \code{To\allowbreak{}Query\allowbreak{}String}, migration SQL
  via differ and generator & no \\
  \tablerule
  Snapshot tests & Code generator as a string and as a round trip (Roslyn) & no \\
  \tablerule
  Integration tests & Real behavior: RLS, roles, interceptors (Testcontainers) & yes
  (Docker) \\
\end{datatable}

\section{Test helpers}

Tests build many contexts with different \code{On\allowbreak{}Model\allowbreak{}Creating}.
Because EF caches the model per internal provider, every test must get its own provider;
that is what
\code{Enable\allowbreak{}Service\allowbreak{}Provider\allowbreak{}Caching(\allowbreak{}false)}
is for:

\begin{sourcecode}[tests/\allowbreak{}.\allowbreak{}.\allowbreak{}.\allowbreak{}/\allowbreak{}Test\allowbreak{}Model.\allowbreak{}cs (\allowbreak{}shortened, simplified)]{csharp}
public static TestContext Create(
    Action<TenancyOptionsBuilder>? tenancy = null,
    Action<ModelBuilder>? model = null,
    bool cacheServiceProvider = false,
    Action<DbContextOptionsBuilder>? configure = null)
{
    var builder = new DbContextOptionsBuilder<TestContext>()
        .UseNpgsql("Host=localhost;Database=unused")       // no connection needed
        .UseAcmeTenancy(tenancy)
        .EnableServiceProviderCaching(cacheServiceProvider);
    configure?.Invoke(builder);
    return new TestContext(builder.Options, model);
}

public static IReadOnlyList<string> MigrationSql(DbContext? source, DbContext target)
{
    var operations = target.GetService<IMigrationsModelDiffer>().GetDifferences(
        source?.GetService<IDesignTimeModel>().Model.GetRelationalModel(),
        target.GetService<IDesignTimeModel>().Model.GetRelationalModel());

    return target.GetService<IMigrationsSqlGenerator>()
        .Generate(operations, target.GetService<IDesignTimeModel>().Model)
        .Select(c => c.CommandText.Trim()).ToList();
}
\end{sourcecode}

\begin{important}[Use the design-time model]
  Always use the \textbf{design-time model} for migration tests
  (\code{IDesign\allowbreak{}Time\allowbreak{}Model}). \code{context.\allowbreak{}Model} is
  the lean runtime model; annotations that the annotation provider only passes on at design
  time are missing from it (failure case in
  chapter~\ref{ch:declarative-sql-from-annotations}).
\end{important}

\begin{note}[Why not SQLite or InMemory?]
  Tests against SQLite or the InMemory provider are tempting because they need no Docker.
  For a plugin they prove little: InMemory is not relational, so type mappings, translators
  and migrations never run; SQLite has a different SQL dialect, other type mappings and no
  Row Level Security. A provider-specific plugin is tested with its own provider: without a
  database (connection string only) for everything up to the SQL text, and against the real
  database for behavior.
\end{note}

\section{The snapshot round trip}

The most valuable test for design-time code: generate the snapshot, compile it with Roslyn,
build the model from it and diff it against the original. Any discrepancy between code
generator and Fluent API would otherwise produce a phantom migration for every user:

% source: tests/Acme.EntityFrameworkCore.Tenancy.Tests/SnapshotTests.cs
\begin{sourcecode}[tests/\allowbreak{}.\allowbreak{}.\allowbreak{}.\allowbreak{}/\allowbreak{}Snapshot\allowbreak{}Tests.\allowbreak{}cs (\allowbreak{}excerpt)]{csharp}
[Fact]
public void Snapshot_roundtrip_produces_no_differences()
{
    using var ctx = CreateContext();
    var snapshot = Compile(GenerateSnapshot(ctx));

    // As in EF's migrator: finalize and initialize
    var model = snapshot.Model;
    if (model is IMutableModel mutable) model = mutable.FinalizeModel();
    model = ctx.GetService<IModelRuntimeInitializer>()
        .Initialize(model, designTime: true, validationLogger: null);

    var differences = ctx.GetService<IMigrationsModelDiffer>().GetDifferences(
        model.GetRelationalModel(), ctx.DesignModel().GetRelationalModel());

    Assert.Empty(differences);
}
\end{sourcecode}

\chapter{Versioning and compatibility}\label{ch:versioning-and-compatibility}

\section{Package version and supported EF version}

The sample versions plugin and handbook together: the package version equals the book
edition, packages 1.1.0 belong to edition~1.1. That way every code excerpt belongs to exactly
one package state. Which EF version a state supports is therefore not part of the version
number but of the packages' dependency range and the compatibility table in the README: plugin
1.x supports EF Core~10. Moving to a new EF major version is a breaking change for users and
gets a new major version, 2.0 for EF Core~11, together with a new book edition. Many plugins
tie their major version to EF Core's instead (10.x for EF Core~10); that shows the matching
combination in the number. Both ways work as long as the dependencies are limited to one EF
major version. A property keeps the range in one place so that CI can override it for the
patch channel (section “Patches and previews in CI”):

\begin{sourcecode}[Directory.\allowbreak{}Packages.\allowbreak{}props (\allowbreak{}excerpt)]{xml}
<PropertyGroup>
  <EFCoreVersion Condition="'$(EFCoreVersion)' == ''">[10.0.0,11.0.0)</EFCoreVersion>
  <CentralPackageFloatingVersionsEnabled>true</CentralPackageFloatingVersionsEnabled>
</PropertyGroup>
<PackageVersion Include="Microsoft.EntityFrameworkCore" Version="$(EFCoreVersion)" />
<PackageVersion Include="Npgsql.EntityFrameworkCore.PostgreSQL" Version="$(EFCoreVersion)" />
\end{sourcecode}

\section{Dealing with internal APIs}

Plugins rarely get by without internal APIs: the sample derives from
\code{Npgsql\allowbreak{}Migrations\allowbreak{}Sql\allowbreak{}Generator},
\code{Npgsql\allowbreak{}Annotation\allowbreak{}Provider} and
\code{Npgsql\allowbreak{}Annotation\allowbreak{}Code\allowbreak{}Generator} and uses
\code{Npgsql\allowbreak{}Options\allowbreak{}Extension}; in total, the PostgreSQL package
touches 13 internal types, the SQL Server package 2 and the core none (inventory in the
upgrade playbook). Such types can change even in minor versions. EF reports their use with
warning \textbf{EF1001}.

\begin{datatable}{H{0.80}H{1.20}}
  \textbf{Measure} & \textbf{Effect} \\
  \tablehead
  Look for a public alternative & Every internal API avoided is one risk less. \\
  \tablerule
  Bundle internal access & A few classes encapsulate it; a break affects one place. \\
  \tablerule
  Set
  \code{<\allowbreak{}No\allowbreak{}Warn>EF1001<\allowbreak{}/\allowbreak{}No\allowbreak{}Warn>}
  deliberately & Project-wide and documented, not scattered per line. \\
  \tablerule
  Limit the version range & Prevents users from getting untested combinations. \\
  \tablerule
  CI against the newest patches and previews & Shows breaks before users report them; the
  channels are described in section “Patches and previews in CI”. \\
  \tablerule
  Round trip and SQL tests & Detect behavior changes the compiler does not see. \\
\end{datatable}

\begin{note}[Multi-targeting]
  Supporting several EF major versions at once is possible through multi-targeting, but
  doubles test effort and conditional compilation. For most plugins, one release branch per
  EF major version is simpler.
\end{note}

\section{Evolving annotation formats}

Everything a plugin writes into annotations ends up in its users' model snapshots, often
long before the next upgrade. If a new plugin version serializes the same configuration
differently (an additional JSON property, a different order, another enum spelling), the
differ compares two different strings. Every user then gets a migration that drops and
recreates every policy without any actual change. The serialized format is therefore part of
the public API, just like the methods.

\begin{datatable}{H{0.79}H{1.21}}
  \textbf{Rule} & \textbf{How} \\
  \tablehead
  Pin the format with a test & A golden-value test compares the serialized form character by
  character. \\
  \tablerule
  Read tolerantly & Missing properties become defaults, unknown ones are ignored (the
  default behavior of System.Text.Json). \\
  \tablerule
  Only add, and do not write defaults & New optional properties with
  \code{[Json\allowbreak{}Ignore(\allowbreak{}Condition =
  When\allowbreak{}Writing\allowbreak{}Default)]} keep existing annotations identical. \\
  \tablerule
  Real format changes only with a major version & Document them, ideally together with the
  EF major upgrade, when users expect migrations anyway. \\
\end{datatable}

% source: tests/Acme.EntityFrameworkCore.Tenancy.Tests/AnnotationFormatTests.cs
\begin{sourcecode}[tests/\allowbreak{}.\allowbreak{}.\allowbreak{}.\allowbreak{}/\allowbreak{}Annotation\allowbreak{}Format\allowbreak{}Tests.\allowbreak{}cs (\allowbreak{}excerpt)]{csharp}
[Fact]
public void Serialized_policy_format_is_stable()
{
    var policy = new RlsPolicy("support_read", PolicyCommand.Select, Permissive: false,
        Roles: ["shop_support"], Using: "true", WithCheck: null);

    // Golden value: changing it is a breaking change for existing snapshots
    Assert.Equal(
        """{"Name":"support_read","Command":"Select","Permissive":false"""
        + ""","Roles":["shop_support"],"Using":"true","WithCheck":null}""",
        policy.Serialize());
}
\end{sourcecode}

Two further tests check tolerant reading in both directions. The snapshot round trip from
chapter~\ref{ch:test-strategy} complements them: the round trip shows that the current code
generator and Fluent API agree, the golden value shows that the next version still agrees
with the snapshots users already have.

\section{Failure classes in an upgrade}

An upgrade to a new EF major version rarely breaks a plugin in just one place, and not every
break announces itself. Knowing the failure classes tells you which test finds them, and
above all which one does not:

  \tablerule

The third row is the most dangerous. Many of the sample's tests do not check the plugin but
the behavior of EF that the plugin and this book rely on. In an upgrade they are more
valuable than any other test, because they report exactly what no compiler sees.

\section{The upgrade playbook}

The workflow is described for the move from EF Core~10 to EF Core~11, but it applies to every
major version: the numbers are interchangeable, the order is not. Beforehand, the previous
line is frozen in a release branch; it keeps getting patches for its EF version while
\code{main} moves to the new one.

\begin{sourcecode}[Step~1: branch and versions]{text}
git switch -c release/1.x main && git push -u origin release/1.x
git switch main

global.json               "version": "11.0.100"
Directory.Build.props     <TargetFramework>net11.0</TargetFramework>
                          <VersionPrefix>2.0.0</VersionPrefix>
Directory.Packages.props  <EFCoreVersion ...>[11.0.0,12.0.0)</EFCoreVersion>
\end{sourcecode}

Which target framework an EF version requires follows no fixed rule: EF Core~9 targets
\code{net8.\allowbreak{}0}, EF Core~10 \code{net10.\allowbreak{}0}, the release
candidates of EF Core~11 \code{net11.\allowbreak{}0}
(\href{https://learn.microsoft.com/en-us/ef/core/what-is-new/}{EF Core releases and planning}). Before upgrading, look into the packages of
EF \emph{and} the provider: which frameworks do they offer, which SDK do they need? In the
sample EF Core~11 requires \code{net11.\allowbreak{}0}, so target framework, SDK and
packages change together; a new EF package could not even be restored on the old target
framework.

  \tablehead

Two commands are enough for steps 2 and 3. The second lifts the project-wide suppression of
EF1001 for this build only and thus shows every place where the plugin touches internal
API:

\begin{sourcecode}[Steps~2 and 3]{text}
# Compiler errors by code
dotnet build -c Release 2>&1 | grep -oE "error [A-Z]+[0-9]+" | sort | uniq -c | sort -rn

# Inventory of internal API: NoWarn without EF1001 (EF9100 stays suppressed)
dotnet build -c Release --no-incremental -p:NoWarn=EF9100 2>&1 \
  | grep -oE "EF1001: [A-Za-z.]+" | sort | uniq -c | sort -rn
\end{sourcecode}

\begin{tip}[Explain deviations, do not test them away]
  If an SQL or behavior test fails after the upgrade, it is tempting to just adjust the
  expectation. Every deviation must be explained first, though: is it an improvement in EF,
  a break in the plugin, or changed semantics that affect users? Only the answer decides
  whether the test, the code or the documentation changes.
\end{tip}

\section{Patches and previews in CI}

Version ranges solve only part of the problem. NuGet takes the \emph{lowest} version of a
range that satisfies all dependencies; the regular CI therefore tests against the beginning
of the line, while users get newer patches. The sample's CI therefore works with three
channels:

\begin{datatable}{H{0.87}H{1.27}H{1.07}H{0.79}}
  \textbf{Channel} & \textbf{Trigger and packages} & \textbf{Purpose} & \textbf{On failure} \\
  \tablehead
  Regular (\code{ci.\allowbreak{}yml}) & Every push and pull request; lowest version of the
  range & The line the plugin is built against & Required check \\
  \tablerule
  Patches (\code{compatibility.\allowbreak{}yml}) & Weekly and manually;
  \code{-p:EFCore\allowbreak{}Version=10.0.*}, stable packages only & Newest patches of the
  plugin's own line & Investigate, patch release \\
  \tablerule
  Next major version & Separate job, scheduled; previews and RCs & See breaks months before
  the release & Not a required check \\
\end{datatable}

The patch channel is active in the sample. Its first run already showed a real finding: the
plugin itself ran with EF Core~10.0.14, but test and sample projects could not be restored
because they had pinned companion packages to 10.0.0 and a Roslyn version of their own.
Since then, these packages follow \code{EFCore\allowbreak{}Version}.

A channel for the next major version is deliberately not active in the sample: it works with
prereleases. Whoever sets one up follows four rules so that regular releases are never
coupled to preview packages:

\begin{datatable}{H{0.85}H{1.15}}
  \textbf{Rule} & \textbf{Why} \\
  \tablehead
  Switch everything through global properties of this job: SDK, target framework and
  \code{EFCore\allowbreak{}Version} & The defaults in the project files stay stable; a
  preview package can never get into a regular build \\
  \tablerule
  Change SDK, target framework and packages together & With the old target framework the
  restore already fails; such a job can never turn green \\
  \tablerule
  Never pack or publish & Releases come only from regular builds of the release branches \\
  \tablerule
  Not a required check & Previews break regularly; the job is an early warning that opens an
  issue, not a gate for pull requests \\
\end{datatable}

\begin{sourcecode}[Job for the next EF version (\allowbreak{}sketch,\allowbreak{} not in the repository)]{text}
  ef-next:
    runs-on: ubuntu-latest
    continue-on-error: true                 # early warning, not a required check
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with: { dotnet-version: 11.0.x, dotnet-quality: preview }
      - run: dotnet new globaljson --sdk-version "$(dotnet --version)" --force
      - name: Build against the next EF Core version (never packed or published)
        run: dotnet build -c Release -p:TargetFramework=net11.0 -p:EFCoreVersion=11.0.0-*
      - run: >
          dotnet test tests/Acme.EntityFrameworkCore.Tenancy.Tests -c Release --no-build
          -p:TargetFramework=net11.0
\end{sourcecode}

Third-party test dependencies such as EFCore.NamingConventions often ship later for the new
version and can block this job's restore. Exclude such tests in the preview channel instead
of switching the channel off.

\section{NuGet advisories and transitive dependencies}\label{sec:nuget-advisories}

A plugin ships not only its own code but also its dependency graph. NuGet audit reports known
vulnerabilities as warnings NU1901 to NU1904
(\href{https://learn.microsoft.com/en-us/nuget/concepts/auditing-packages}{NuGet: Auditing package dependencies}).
What matters is \emph{whom} a finding affects. \code{dotnet nuget why} finds out, showing the path
from the direct dependency to the affected package. The sample had three cases:

\begin{datatable}{H{0.75}H{1.05}H{0.70}H{1.50}}
  \textbf{Package} & \textbf{Origin} & \textbf{Affects} & \textbf{Decision} \\
  \tablehead
  \code{System.\allowbreak{}Security.\allowbreak{}Cryptography.\allowbreak{}Pkcs} 9.0.4 &
  EF Core SqlServer → \code{Microsoft.\allowbreak{}Data.\allowbreak{}SqlClient} 6.1 & Consumers of
  the SQL Server package & No patch and no SqlClient version (not even 7.x) brings 9.0.21 yet.
  Hence a direct dependency on 9.0.22 in the SQL Server package; it ends up in the nuspec and
  fixes the application's graph. \\
  \tablerule
  \code{Cryptography.\allowbreak{}Xml}/\code{Pkcs} 9.0.0 & EF Core Design 10.0.0 → MSBuild
  17.14, Workspaces.MSBuild 4.14 & Tooling only: tests, sample & Newer Design patches need other
  MSBuild packages but would pull EF itself along and end the test of the minimum version.
  Hence \code{Xml} 9.0.22 in test and sample projects only. \\
  \tablerule
  \code{SSH.\allowbreak{}NET} 2024.2.0 & Testcontainers 4.6 & Tests only & Testcontainers 4.16
  within the same major version; brings 2026.0.0. \\
\end{datatable}

Every direct dependency on what is really a transitive package is listed in
\code{Directory.\allowbreak{}Packages.\allowbreak{}props} with its origin, the advisory and the
criterion for when it can go again. Nothing is suppressed: neither \code{NoWarn} nor a disabled
audit makes a dependency safe, they only hide the finding. Both CI channels also run
\code{dotnet list package -\allowbreak{}-vulnerable -\allowbreak{}-include-transitive} and fail on
any finding. The regular run still builds against EF Core 10.0.0, the compatibility run against
the newest 10.0.x patch; the fixes are minimum versions and apply in both. For tooling there is an
interaction: \code{Microsoft.\allowbreak{}Entity\allowbreak{}Framework\allowbreak{}Core.\allowbreak{}Tasks}
treats the audit warnings as errors on publish, so NativeAOT fails with EF Design 10.0.0
(page~\pageref{sec:consumer-test}).

\section{Upgrade checklist}

\begin{checklist}
  \item Create a release branch for the old line; move \code{main} to the new version.
  \item Change SDK, target framework, \code{EFCore\allowbreak{}Version}, companion packages and
    \code{Version\allowbreak{}Prefix} together.
  \item Count compiler errors by code and work through them class by class.
  \item Create the EF1001 inventory and check every place against the new sources, including
    those that compile.
  \item Check lifetimes against EF's service table; read derived provider classes for new
    virtual overloads.
  \item Model, SQL, migration, snapshot and compiled model tests green; every deviation
    explained.
  \item Annotation formats unchanged (golden-value tests).
  \item New IL warnings for trimming and AOT read.
  \item Integration tests against real databases with the new providers.
  \item Public API diff checked; intended breaks entered.
  \item Benchmarks of both lines compared.
  \item CHANGELOG, compatibility table and support period of the old line documented.
\end{checklist}

\chapter{The checklist from A to Z}\label{ch:the-checklist-from-a-to}

For every new plugin, in the order of development. Each item sums up a rule; the reasoning is in the chapters named under each heading.

\section{Architecture}

\noindent Details: chapters~\ref{ch:the-sample-scenario}, \ref{ch:choosing-the-right-extension-point}.

\begin{checklist}
  \item Decide the level: helpers, model helpers, real plugin or provider?
  \item Separate core and provider packages; types for entity assemblies go into the core.
  \item For every extension point, look for a plugin interface first, replace only then.
  \item Check every mechanism against the simpler alternative with the decision guide
    (chapter~\ref{ch:choosing-the-right-extension-point}).
\end{checklist}

\section{Options}

\noindent Details: chapter~\ref{ch:the-options-extension}.

\begin{checklist}
  \item Extension immutable with copy constructor and virtual Clone.
  \item All model-relevant options in the hash, nothing that varies per context.
  \item Validate for preconditions (provider, combinations).
  \item Maintain LogFragment and PopulateDebugInfo.
  \item Use method in the namespace Microsoft.EntityFrameworkCore, generic and non-generic.
\end{checklist}

\section{Services}

\noindent Details: chapters~\ref{ch:registering-services}, \ref{ch:state-lifetimes-and-thread-safety}.

\begin{checklist}
  \item Registration through the services builder (lifetimes from EF's table).
  \item Decorate single services where the public interface suffices
    (chapter~\ref{ch:registering-services}).
  \item Otherwise Replace, and offer the logic publicly and virtually.
  \item ISingletonOptions for singleton services, registered twice.
  \item Classify every piece of state according to chapter~\ref{ch:state-lifetimes-and-thread-safety}: request data never
    in options, hash, model, singleton or translated query.
  \item Reset scoped services with state for pooling (IResettableService).
  \item App dependencies via AddInterceptors, document pooling behavior.
\end{checklist}

\section{Model}

\noindent Details: chapters~\ref{ch:annotations-and-fluent-api}, \ref{ch:conventions}, \ref{ch:model-validation}.

\begin{checklist}
  \item Annotations with a prefix, simple values only, no stored defaults.
  \item Implement the Fluent API non-generically, delegate generically.
  \item Convention builder overloads for ConfigurationSource.
  \item Conventions at ModelFinalizing when they depend on the finished model.
  \item Attributes in the core package, attribute conventions in the provider package.
  \item Validation as IModelFinalizedConvention: throw on errors, warn on questionable
    cases.
  \item Check table mappings against the support matrix and reject unsupported ones while the
    model is built (page~\pageref{sec:supported-table-mappings}).
\end{checklist}

\section{Type mappings}

\noindent Details: chapter~\ref{ch:type-mappings-and-value-converters}.

\begin{checklist}
  \item Protected parameter constructor and Clone override.
  \item Literal generation for model and provider type.
  \item Public static Default property, shared converter instance.
  \item Shared value comparer instances, otherwise EF creates them through reflection (NativeAOT).
  \item JsonValueReaderWriter with Instance and ConstructorExpression.
\end{checklist}

\section{Queries}

\noindent Details: chapters~\ref{ch:the-query-pipeline}, \ref{ch:translating-methods-and-members}.

\begin{checklist}
  \item EF.Functions methods in the core, translation in the provider package.
  \item Translators: null for foreign methods, correct nullability, set type mappings.
  \item IEvaluatableExpressionFilterPlugin for methods without data reference.
  \item Never insert run-time values at translation time (query cache, AOT).
\end{checklist}

\section{Run time}

\noindent Details: chapters~\ref{ch:interceptors}, \ref{ch:diagnostics-and-logging}.

\begin{checklist}
  \item Implement interceptors synchronously and asynchronously.
  \item Tell the tracking flag from an actual change of value
    (page~\pageref{sec:tracking-flag-versus-value}).
  \item Singleton interceptors stateless and thread-safe.
  \item Register singleton interceptors in ApplyServices or pass one shared instance, never a
    new one per context; get per-request data on every call through the context.
  \item Own event IDs in an own range, EventDefinitions cached.
  \item Security-relevant cases as warnings, escalatable via ConfigureWarnings.
  \item Where hooks cannot run, offer an explicit API (e.g. ApplyTenantSession).
\end{checklist}

\section{Migrations \& design time}

\noindent Details: chapters~\ref{ch:how-migrations-work}, \ref{ch:design-time-services}.

\begin{checklist}
  \item Declarative via annotation provider (design time only) and SQL generator.
  \item Escape identifiers, literals via type mappings, validate self-generated SQL.
  \item Custom operations idempotent, extensions in the migrations namespace.
  \item Remove schema-bound objects before renames and recreate them with the final names
    afterwards (page~\pageref{sec:sqlserver-schema-bound-changes}).
  \item DesignTimeServicesReference with forProvider; code generator removes annotations.
  \item Check compiled models: Default, Instance, runtime annotations.
\end{checklist}

\section{Quality}

\noindent Details: chapters~\ref{ch:test-strategy}, \ref{ch:versioning-and-compatibility}, \ref{ch:packaging-and-documentation}.

\begin{checklist}
  \item Model, SQL, snapshot round trip and integration tests.
  \item Caching test with different options; test for no phantom migration.
  \item Version range per EF major, CI against the newest patches and previews, EF1001
    deliberately; upgrades following the playbook (chapter~\ref{ch:versioning-and-compatibility}).
  \item XML docs, SourceLink, symbols, README, CHANGELOG, limitations documented.
  \item Check the packages as a consumer: tooling, compiled model, NativeAOT
    (page~\pageref{sec:consumer-test}).
  \item Pin serialized annotation formats with golden-value tests.
  \item Test together with popular plugins (naming conventions, decorators) and check the
    coexistence with a second plugin in both orders (chapter~\ref{ch:registering-services}).
\end{checklist}

\section{Advanced (part~\ref{part:VIII})}

\noindent Details: chapters~\ref{ch:row-level-security-in-production}, \ref{ch:tenant-safe-relationships}, \ref{ch:retrofitting-and-operating}.

\begin{checklist}
  \item Document paths that bypass interceptors (ExecuteUpdate, raw SQL).
  \item Configure value generators with HasValueGeneratorFactory(Type) (compiled models).
  \item Check conventions for complex types and JSON columns.
  \item Document and test the order of custom migration operations.
  \item Consider idempotent scripts and suppressTransaction.
  \item Document operational assumptions (roles, pooling, transaction pooling).
  \item Document context lifetimes: factories, background jobs, open connections.
  \item Cross-tenant access only through separate roles, never through app switches.
  \item Document the threat model: what is protected and what is not
    (page~\pageref{sec:threat-model}).
  \item Tenant-safe relationships: composite foreign keys, unique per tenant.
  \item Retrofit existing tables in two migrations with a guard.
  \item Measure hot paths (interceptors), do not guess.
  \item CI with a patch channel, a preview channel only as an early warning, public API
    analyzer as errors.
\end{checklist}

\section{Deep extensions (part~\ref{part:IX})}

\noindent Details: chapters~\ref{ch:custom-sql-expression-nodes}, \ref{ch:a-second-provider-sql-server}.

\begin{checklist}
  \item Custom SQL nodes: VisitChildren, Update, Quote, Print, Equals/GetHashCode.
  \item Handle custom nodes in the SQL generator AND in the nullability processor.
  \item Aggregates: handle predicates, DISTINCT and empty sets deliberately.
  \item Choose runtime annotations deliberately, filter design-time annotations.
  \item Scaffolding: read the plugin's schema objects from the database.
  \item Provider-neutral building blocks into the core, differences into provider packages.
\end{checklist}
