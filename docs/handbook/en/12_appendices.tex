\chapter{Extension points and lifetimes}\label{app:A}

This appendix leads from a mechanism to its properties and to the chapter that covers it. The
opposite direction, from the problem to the mechanism, is taken by the decision guide in
chapter~\ref{ch:choosing-the-right-extension-point}. Lifetime and cardinality come from
EF Core~10's service tables
(\code{Entity\allowbreak{}Framework\allowbreak{}Services\allowbreak{}Builder},
\code{Entity\allowbreak{}Framework\allowbreak{}Relational\allowbreak{}Services\allowbreak{}Builder},
\code{Entity\allowbreak{}Framework\allowbreak{}Relational\allowbreak{}Design\allowbreak{}Services\allowbreak{}Builder}),
the statements about provider implementations from Npgsql~10;
\code{Service\allowbreak{}Registration\allowbreak{}Tests} checks the sample's registrations
against the same tables.

\begin{datatable}{H{0.55}H{1.45}}
  \textbf{Marker} & \textbf{Meaning} \\
  \tablehead
  Singleton, scoped & Once per internal provider or once per context instance, with pooling
  across several requests (chapter~\ref{ch:state-lifetimes-and-thread-safety}); “DT”: in the
  service provider of \code{dotnet ef} \\
  \tablerule
  multiple, single & Plugin interface, EF asks all registrations; or single service with
  exactly one winner \\
  \tablerule
  public, provider base, pubternal & As in the decision guide: public API only; replacing
  means inheriting from the provider's implementation; even EF's own type is internal \\
  \tablerule
  \code{Try\allowbreak{}Add}, \code{Replace}, \code{Replace\allowbreak{}Service} & Added or
  replaced in the extension's \code{Apply\allowbreak{}Services}; replaced by the application
  on the options builder \\
  \tablerule
  † & Elevated upgrade risk: replacing or deriving touches internal API of EF or Npgsql
  (EF1001, upgrade playbook in chapter~\ref{ch:versioning-and-compatibility}) \\
  \tablerule
  ● ◐ ○ & Preferred mechanism; use with care; last resort \\
  \tablerule
  \textbf{exclusive} & Replacing rules out every other plugin that replaces the same service
  (compatibility matrix in chapter~\ref{ch:registering-services}) \\
\end{datatable}

\chapter{Exercises with solutions}\label{app:E}

Each exercise asks a question that the text answers and names a test of the sample that records
the answer. To check a solution, change the sample as the exercise describes and watch which test
fails.

\section{Exercise 1: Convention versus explicit configuration}

A user configures a policy for \code{Order} with the name of the plugin's policy:
\code{Has\allowbreak{}Policy(\allowbreak{}\textquotedbl{}tenant\_\allowbreak{}isolation\textquotedbl{},
p => p.\allowbreak{}Using(\allowbreak{}\textquotedbl{}true\textquotedbl{}))}. The isolation
convention sets the same annotation at \code{Model\allowbreak{}Finalizing}. Which configuration
applies? What changes if the convention sets the annotation with
\code{Set\allowbreak{}Annotation} directly on the entity type instead of through the builder?

\begin{note}[Solution]
  The explicit configuration applies. The convention builder sets annotations with
  \code{Configuration\allowbreak{}Source.\allowbreak{}Convention} and leaves an explicit
  configuration in place; \code{Has\allowbreak{}Annotation} then returns \code{null}
  (chapter~\ref{ch:conventions}). \code{Set\allowbreak{}Annotation} on the type knows no
  configuration source and would silently overwrite the user's policy.
  Check: \code{Convention\allowbreak{}Tests.\allowbreak{}Explicit\allowbreak{}\_policy\allowbreak{}\_with\allowbreak{}\_same\allowbreak{}\_name\allowbreak{}\_wins\allowbreak{}\_over\allowbreak{}\_convention}.
\end{note}

\section{Exercise 2: The tenant in the cache key}

A plugin includes the current tenant in
\code{Get\allowbreak{}Service\allowbreak{}Provider\allowbreak{}Hash\allowbreak{}Code}, so that
every tenant gets “its” model. What happens with 1000 tenants?

\begin{note}[Solution]
  Every tenant gets an internal service provider of its own with a model of its own. From the
  21st provider on, EF throws the
  \code{Many\allowbreak{}Service\allowbreak{}Providers\allowbreak{}Created\allowbreak{}Warning} as
  an error by default, and every provider keeps model, query cache and services in memory. The
  tenant is per-request state and belongs in the interceptor
  (chapter~\ref{ch:state-lifetimes-and-thread-safety}); only when the \emph{model} really
  differs does a model cache key of its own help (chapter~\ref{ch:models-per-runtime-context}).
  Check: \code{State\allowbreak{}And\allowbreak{}Lifetime\allowbreak{}Tests.\allowbreak{}Tenant\allowbreak{}\_in\allowbreak{}\_the\allowbreak{}\_service\allowbreak{}\_provider\allowbreak{}\_key\allowbreak{}\_needs\allowbreak{}\_a\allowbreak{}\_provider\allowbreak{}\_per\allowbreak{}\_tenant}.
\end{note}

\section{Exercise 3: Nullability of a translator}

Without a tenant, \code{Current\allowbreak{}Tenant(\allowbreak{})} becomes \code{NULL} in SQL.
Someone therefore declares the expression nullable. What does
\code{o.\allowbreak{}Tenant\allowbreak{}Id != EF.\allowbreak{}Functions.\allowbreak{}Current\allowbreak{}Tenant(\allowbreak{})}
return without a tenant, for example under the reporting role without RLS?

\begin{note}[Solution]
  For a nullable expression EF adds C\# semantics: \code{<>} becomes a comparison with
  \code{OR \allowbreak{}.\allowbreak{}.\allowbreak{}. IS NULL}, and without a tenant the condition is
  true for \emph{all} rows. Declared not nullable, it stays a plain \code{<>}, which is never true
  with \code{NULL}: no rows, the safe direction
  (chapter~\ref{ch:translating-methods-and-members}).
  Check: \code{Query\allowbreak{}Translation\allowbreak{}Tests.\allowbreak{}Inequality\allowbreak{}\_with\allowbreak{}\_Current\allowbreak{}Tenant\allowbreak{}\_never\allowbreak{}\_matches\allowbreak{}\_without\allowbreak{}\_a\allowbreak{}\_tenant}.
\end{note}

\section{Exercise 4: A migration diff on SQL Server}

The tenant column is renamed with
\code{Has\allowbreak{}Column\allowbreak{}Name(\allowbreak{}\textquotedbl{}Mandant\textquotedbl{})}.
In which order does EF generate the operations, and why is it not enough to recreate the security
policy at the \code{Alter\allowbreak{}Table\allowbreak{}Operation}?

\begin{note}[Solution]
  EF generates \code{Rename\allowbreak{}Column}, \code{Rename\allowbreak{}Index} and only then the
  \code{Alter\allowbreak{}Table\allowbreak{}Operation} with the changed annotation. The
  schema-bound policy, however, already blocks the \code{sp\_\allowbreak{}rename}. The generator
  has to wrap the whole operation list
  (page~\pageref{sec:sqlserver-schema-bound-changes}).
  Check: \code{Sql\allowbreak{}Server\allowbreak{}Migration\allowbreak{}Order\allowbreak{}Tests}
  without a database, \code{Sql\allowbreak{}Server\allowbreak{}Migration\allowbreak{}Tests}
  against SQL Server.
\end{note}

\section{Exercise 5: An update from the API}

An API receives an order and saves it with \code{Update}. Why does EF mark the tenant property as
modified, and what stops an attacker from sending the ID of a foreign order with the own tenant?

\begin{note}[Solution]
  \code{Update} of an untracked entity marks every property; original and current value are the
  same. That is no change of tenant; the interceptor checks the value only
  (page~\pageref{sec:tracking-flag-versus-value}). Against the foreign ID it does not help,
  because without accessing the database it cannot know whom the row belongs to. The
  \code{UPDATE} does not see the row because of the policy, changes zero rows, and EF reports a
  concurrency error. Check: \code{Detached\allowbreak{}Update\allowbreak{}Tests} against
  PostgreSQL.
\end{note}
