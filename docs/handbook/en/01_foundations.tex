\section*{About this book}

Many EF Core extensions start out as a handful of extension methods and then grow without a
plan. If you understand how EF Core is built internally, however, you can write extensions
that feel like part of EF Core itself: they are configured through the options, run inside
the internal service provider, translate custom functions to SQL, generate migrations, write
readable snapshots, and combine cleanly with other plugins.

This book explains each of these building blocks in two layers. First comes the
\textbf{principle}: how does the mechanism work in EF Core, which variants exist, and what
do you need to watch out for? Then comes the \textbf{implementation} in the sample plugin,
with the code that is also in the repository. The chapters build on each other, but can also
be read individually as a reference. If you come with a concrete problem and are looking for
the right mechanism, start with the decision guide in
chapter~\ref{ch:choosing-the-right-extension-point}. The code in the repository and the snippets in this
edition use English comments and messages. Each snippet's label names the file.

\section{What a level 3 plugin can do}

A complete plugin can extend EF Core at practically every point: it can make new CLR types
available as column types, translate custom functions in LINQ to SQL, adapt the model
automatically through conventions, accept metadata through the Fluent API and attributes,
validate the model, intervene when saving and when opening connections, log its own events,
add custom SQL to migrations and extend the \code{dotnet ef} tooling. The sample in this
book uses every one of these possibilities.

\begin{tip}[Role models in the ecosystem]
  Before writing your own, look at existing plugins. \textbf{EFCore.NamingConventions} is a
  small, clean convention plugin. The \textbf{NetTopologySuite} plugin in the EF Core
  repository shows type mappings and translations. Npgsql's \textbf{NodaTime} plugin shows a
  provider-specific plugin activated through the provider's options builder.
\end{tip}

\section{Two containers: the internal service provider}

Every \code{Db\allowbreak{}Context} resolves its infrastructure from an \textbf{internal}
\code{IService\allowbreak{}Provider}. It is separate from the application's DI container and
contains several hundred services: type mapping, model building, the query pipeline, change
tracking, the update pipeline, migrations. A plugin hooks in by registering additional
services in this container or replacing existing ones. The book also calls it the
\emph{internal provider} for short; that never means the database provider such as Npgsql.

\begin{flowdiagram}
  \flowstep{DbContextOptions}{Provider extension (UseNpgsql) and plugin extensions
  (UseAcmeTenancy)}
  \flowstep{ServiceProviderCache}{Finds a matching internal provider by hash, or builds one}
  \flowstep{ApplyServices()}{Each extension registers its services in the new provider}
  \flowstep{Internal service provider}{Cached and shared by all matching contexts}
  \flowstep{Model (cached)}{Built once per provider and context type: conventions, type
  mappings, validation}
  \flowstep{Query, SaveChanges, Migrations}{Run with the services of this provider}
\end{flowdiagram}

Two caches are decisive here. The \textbf{service provider} is cached based on the options:
contexts with the same configuration share one provider. The \textbf{model} is cached per
provider (and context type). Both make EF Core fast, but they have direct consequences for
plugins, which chapter~\ref{ch:the-options-extension} covers in detail.

The model exists in two forms. The \textbf{design-time model} contains all annotations and
is the basis for migrations and snapshots. At run time, \code{context.\allowbreak{}Model}
returns a lean, read-only \textbf{runtime model} that keeps only the annotations needed at
run time. Which ones these are and how a plugin controls them is shown in
chapters~\ref{ch:declarative-sql-from-annotations} and \ref{ch:property-level-fluent-api-and};
but already in part~\ref{part:model}, plugin code that reads at run time sees only the
runtime model.

\section{Lifetimes}

Every EF service has a fixed lifetime. \textbf{Singleton} here means: once per internal
service provider, not per application. \textbf{Scoped} means: once per context instance. A
singleton must not hold a scoped service, and a service that needs different data per
context must not be a singleton. Appendix~\ref{app:A} lists the lifetimes of all extension
points; chapter~\ref{ch:state-lifetimes-and-thread-safety} summarizes which state belongs where.

\section{The dependencies pattern}

EF services do not receive their dependencies individually, but as a parameter object, such
as \code{Migrations\allowbreak{}Sql\allowbreak{}Generator\allowbreak{}Dependencies} or
\code{Provider\allowbreak{}Convention\allowbreak{}Set\allowbreak{}Builder\allowbreak{}Dependencies}.
When you derive from an EF service, you accept this object in the constructor and pass it
on. EF Core adds new dependencies to the object without breaking constructors. For plugins
this is a blessing: derived services stay compatible across minor versions.

% source: src/Acme.EntityFrameworkCore.Tenancy.PostgreSQL/Migrations/Internal/TenancyMigrationsSqlGenerator.cs
\begin{sourcecode}[Migrations/\allowbreak{}Internal/\allowbreak{}Tenancy\allowbreak{}Migrations\allowbreak{}Sql\allowbreak{}Generator.\allowbreak{}cs (\allowbreak{}header)]{csharp}
public class TenancyMigrationsSqlGenerator : NpgsqlMigrationsSqlGenerator
{
    public TenancyMigrationsSqlGenerator(
        MigrationsSqlGeneratorDependencies dependencies,     // parameter object from EF
        INpgsqlSingletonOptions npgsqlSingletonOptions)      // additionally from the provider
        : base(dependencies, npgsqlSingletonOptions)
    {
    }
\end{sourcecode}

\begin{note}[Code style in the sample]
  All classes in the sample use classic constructors with \code{private readonly} fields and
  \code{Argument\allowbreak{}Null\allowbreak{}Exception.\allowbreak{}Throw\allowbreak{}If\allowbreak{}Null},
  no primary constructors. Their parameters are mutable throughout the class body, offer no
  natural place for validation and hide which state is stored. Classic constructors also
  match the style of EF Core and Npgsql, whose classes a plugin derives from. The only
  exception is positional records such as \code{Rls\allowbreak{}Policy}, where the syntax
  generates real \code{init} properties.
\end{note}

\section{Extend or replace?}

There are two fundamentally different ways to extend EF Core. \textbf{Plugin interfaces}
such as \code{IMethod\allowbreak{}Call\allowbreak{}Translator\allowbreak{}Plugin} or
\code{IConvention\allowbreak{}Set\allowbreak{}Plugin} are designed for exactly this. They
can be registered multiple times, EF queries all registrations, and several plugins coexist.
\textbf{Replacing} means swapping a single service such as
\code{IMigrations\allowbreak{}Sql\allowbreak{}Generator} for a derived class. That is
sometimes unavoidable, but only one replacement can win per context.

\begin{important}[Plugin interfaces before replacement]
  Always check first whether a plugin interface exists. Replacing a single service collides
  with every other plugin that replaces the same service and forces you to derive from the
  provider's implementation. That ties the plugin to one provider and its internal API.
  Chapter~\ref{ch:registering-services} shows how to stay composable anyway.
\end{important}

Chapter~\ref{ch:choosing-the-right-extension-point} classifies every individual extension
point: whether it is a plugin interface or a single service, and which simpler alternative to
consider first.

\section{Warm-up: a complete plugin in five pieces}

Before the large sample, here is the smallest plugin that is still complete. It makes
PostgreSQL's \code{reverse(\allowbreak{})} available in LINQ as
\code{EF.\allowbreak{}Functions.\allowbreak{}Reverse(\allowbreak{}.\allowbreak{}.\allowbreak{}.\allowbreak{})}.
Every later chapter elaborates one of its five pieces:

% source: tests/Acme.EntityFrameworkCore.Tenancy.Tests/MinimalPluginTests.cs
\begin{sourcecode}[tests/\allowbreak{}Acme.\allowbreak{}Entity\allowbreak{}Framework\allowbreak{}Core.\allowbreak{}Tenancy.\allowbreak{}Tests/\allowbreak{}Minimal\allowbreak{}Plugin\allowbreak{}Tests.\allowbreak{}cs (\allowbreak{}1/\allowbreak{}2,\allowbreak{} shortened)]{csharp}
// 1. The function users call in LINQ; it is never executed
public static class ReverseDbFunctionsExtensions
{
    public static string Reverse(this DbFunctions _, string value)
        => throw new InvalidOperationException("Reverse can only be used in LINQ queries.");
}

// 2. The translator turns the method call into a SQL function
//    (chapter "Translating methods and members")
public class ReverseTranslator : IMethodCallTranslator
{
    // Constructor stores the ISqlExpressionFactory in _sql

    public SqlExpression? Translate(
        SqlExpression? instance, MethodInfo method, IReadOnlyList<SqlExpression> arguments,
        IDiagnosticsLogger<DbLoggerCategory.Query> logger)
        => method == ReverseMethod
            ? _sql.Function("reverse", [arguments[1]], nullable: true,
                argumentsPropagateNullability: [true], typeof(string),
                arguments[1].TypeMapping)
            : null;
}

// 3. The plugin hands the translator to EF (chapter "Translating methods and members")
public class ReverseTranslatorPlugin : IMethodCallTranslatorPlugin
{
    public ReverseTranslatorPlugin(ISqlExpressionFactory sql)
    {
        Translators = [new ReverseTranslator(sql)];
    }

    public IEnumerable<IMethodCallTranslator> Translators { get; }
}
\end{sourcecode}

% source: tests/Acme.EntityFrameworkCore.Tenancy.Tests/MinimalPluginTests.cs
\begin{sourcecode}[tests/\allowbreak{}Acme.\allowbreak{}Entity\allowbreak{}Framework\allowbreak{}Core.\allowbreak{}Tenancy.\allowbreak{}Tests/\allowbreak{}Minimal\allowbreak{}Plugin\allowbreak{}Tests.\allowbreak{}cs (\allowbreak{}2/\allowbreak{}2,\allowbreak{} shortened)]{csharp}
// 4. The options extension registers the plugin in EF's internal provider
//    (chapters "The options extension" and "Registering services")
public class ReverseOptionsExtension : IDbContextOptionsExtension
{
    private DbContextOptionsExtensionInfo? _info;

    public DbContextOptionsExtensionInfo Info => _info ??= new ExtensionInfo(this);

    public void ApplyServices(IServiceCollection services)
        => new EntityFrameworkRelationalServicesBuilder(services)
            .TryAdd<IMethodCallTranslatorPlugin, ReverseTranslatorPlugin>();

    public void Validate(IDbContextOptions options)
    {
    }

    // ExtensionInfo: not a provider, no settings -> hash 0, always the same provider
}

// 5. The Use method activates the plugin
//    (chapter "Public API and integration into the application")
public static DbContextOptionsBuilder UseReverse(this DbContextOptionsBuilder builder)
{
    ((IDbContextOptionsBuilderInfrastructure)builder).AddOrUpdateExtension(
        builder.Options.FindExtension<ReverseOptionsExtension>()
        ?? new ReverseOptionsExtension());
    return builder;
}
\end{sourcecode}

\begin{sourcecode}[Usage]{csharp}
options.UseNpgsql(connectionString).UseReverse();

db.Customers.Where(c => EF.Functions.Reverse(c.Name) == "abc");
// SQL: WHERE reverse(c."Name") = 'abc'
\end{sourcecode}

That is all a working plugin needs. EF finds the translator because the extension registers
it in the internal service provider, and every context configured with
\code{Use\allowbreak{}Reverse(\allowbreak{})} shares that provider. Because the argument
references a column, the function needs no evaluatable expression filter
(chapter~\ref{ch:preventing-client-side-evaluation} explains when it does). The test
\code{Minimal\allowbreak{}Plugin\allowbreak{}Tests} checks the translation and that the same
query fails without the plugin. The tenancy plugin consists of exactly these pieces, only
many more of them.

\chapter{The sample scenario}\label{ch:the-sample-scenario}
\versionrisk{stable}

The sample plugin \textbf{Acme.EntityFrameworkCore.Tenancy} makes EF Core multi-tenant with
PostgreSQL. The database itself enforces tenant separation through \textbf{Row Level
Security} (RLS): every table with tenant data gets a policy that only shows rows of the tenant
whose ID is set in the current database session. Mappings in which such a table would lack the
tenant column are rejected by the plugin while the model is built
(page~\pageref{sec:supported-table-mappings}). Even a faulty LINQ query or raw SQL therefore
only sees the rows of the tenant that is set. Whoever can run arbitrary SQL under the
application role, however, can also change the session setting; chapter
\ref{ch:row-level-security-in-production} deals with this limit.

From the user's point of view it looks like this:

\begin{sourcecode}[User's view]{csharp}
public class Order : ITenantOwned               // marker from the core package
{
    public int Id { get; set; }
    public TenantId TenantId { get; set; }      // strongly typed, automatically uuid
    public decimal Total { get; set; }
}

services.AddAcmeTenancy<HttpTenantProvider>();
services.AddDbContext<ShopContext>((sp, o) => o
    .UseNpgsql(connectionString)
    .UseAcmeTenancy(sp, tenancy => tenancy.ApplyQueryFilter()));

// Querying and saving without any tenant logic in application code
db.Orders.Add(new Order { Total = 42 });         // the plugin sets TenantId
var mine = await db.Orders.ToListAsync();        // RLS filters in the database
\end{sourcecode}

\section{Package architecture}

At its heart the plugin consists of four NuGet packages. The \textbf{core package} contains everything
that is independent of the database and that assemblies with entity classes may reference
without pulling in a provider; it works with any EF Core provider. The \textbf{relational
package} adds what every SQL database needs: the session interceptor on the connection and the
check of the table mappings. The \textbf{PostgreSQL package} is the complete
implementation this book uses to explain everything. The \textbf{SQL Server package} uses
the same core and relational layer and shows in chapter~\ref{ch:a-second-provider-sql-server} what a second
provider has to implement itself. A fifth package,
\code{Acme.\allowbreak{}Entity\allowbreak{}Framework\allowbreak{}Core.\allowbreak{}Tenancy.\allowbreak{}Cosmos},
builds on the core alone and shows what carries over to a database without SQL
(chapter~\ref{ch:without-sql-what-carries-over}). Besides these, the small package
\code{Acme.\allowbreak{}Entity\allowbreak{}Framework\allowbreak{}Core.\allowbreak{}Functions.\allowbreak{}Postgre\allowbreak{}SQL}
holds the examples for custom SQL nodes and aggregates; they have nothing to do with
multi-tenancy (chapter~\ref{ch:custom-sql-expression-nodes}).

The parts of this book follow EF Core's architecture: infrastructure, model, queries, run
time, migrations. A concrete problem rarely does. “Every row belongs to a tenant” can be
solved with a query filter, a SaveChanges interceptor, a convention or with policies from
migrations, and each of these solutions has a different price and different gaps. The
sample plugin from chapter~\ref{ch:the-sample-scenario} therefore combines several of them.

This chapter starts from the problem and leads to the right mechanism. It is a map, not a
reference: how a mechanism works is explained in the chapter it names. Appendix~\ref{app:A}
goes the other way: from the mechanism to lifetime, cardinality, API status, registration and
composability. On a first reading, skim the
chapter and come back with a concrete problem.

\section{The lowest depth of intervention}

The most important rule is the same as in “Extend or replace?”
(chapter~\ref{ch:ef-core-s-architecture-from}), only broader: \textbf{choose the lowest
depth of intervention that solves the problem completely.} Each step in the following table
costs more compatibility than the one before:

\begin{datatable}{H{0.62}H{1.28}H{1.10}}
  \textbf{Depth} & \textbf{Means} & \textbf{Price} \\
  \tablehead
  Application & \code{On\allowbreak{}Model\allowbreak{}Creating},
  \code{Configure\allowbreak{}Conventions}, \code{Has\allowbreak{}Db\allowbreak{}Function},
  \code{migration\allowbreak{}Builder.\allowbreak{}Sql(\allowbreak{})}, overriding
  \code{Save\allowbreak{}Changes} & No plugin; every application repeats the code \\
  \tablerule
  Metadata & Annotations and Fluent API extensions & Only take effect once a service reads
  them \\
  \tablerule
  Plugin interface & Conventions, translator, type mapping and filter plugins, interceptors
  & Can be registered multiple times, coexists with other plugins \\
  \tablerule
  Decorating & Wrapping a single service and delegating to it & Only if the public
  interface suffices; the activation order matters \\
  \tablerule
  Replacing & Replacing a single service with a class derived from the provider's & One
  winner per context; ties the plugin to the provider and often to internal API \\
  \tablerule
  Deep intervention & Custom SQL nodes, custom differ, postprocessor & Several single
  services at once; hardly composable with similar plugins \\
\end{datatable}

“Completely” is meant literally. A query filter is simpler than row level security, but it
does not protect against raw SQL (chapter~\ref{ch:bulk-operations-and-the-limits}). The
simpler solution only wins if it gives the same guarantee. Five questions settle whether it
does:

\begin{datatable}{H{0.70}H{1.30}}
  \textbf{Question} & \textbf{Why it matters} \\
  \tablehead
  When does the mechanism run? & During model building once per internal provider, during
  translation once per query shape, during execution every time, at design time only in
  \code{dotnet ef}. This determines which state it may use
  (chapter~\ref{ch:plugin-performance}). \\
  \tablerule
  Is there a simpler alternative? & The lower depth wins if it gives the same guarantee. \\
  \tablerule
  Public or internal? & Internal API (EF1001) can change in any minor version
  (chapter~\ref{ch:versioning-and-compatibility}). \\
  \tablerule
  Multiple or single? & Services that can be registered multiple times coexist with other
  plugins; for a single service exactly one wins. \\
  \tablerule
  Which lifetime? & A singleton may neither hold scoped services nor per-context data; a
  scoped service may do both (chapter~\ref{ch:state-lifetimes-and-thread-safety}). \\
\end{datatable}

\section{The responsible area}

The first step is almost always the question \emph{where} the problem lies. The following
decision tree leads to the responsible area; each area then has its own section with a
table.

\begin{decisiontree}
  \decision{Should users switch the plugin on, configure it or connect it to services of
    their application?}
    {Options extension, services, interceptors from the application
    (page~\pageref{sec:decide-configuration})}
  \decision{Should the model carry metadata, adapt automatically or be validated?}
    {Annotations, Fluent API, conventions, validation (page~\pageref{sec:decide-model})}
  \decision{Is it about a new column type or about values that EF converts or generates?}
    {Type mapping, value converter, value generation (page~\pageref{sec:decide-model})}
  \decision{Should the SQL of a LINQ query change, or the loaded object?}
    {Translators, filter, query interceptor, materialization
    (page~\pageref{sec:decide-queries}, chapter~\ref{ch:materialization-from-rows-to-objects})}
  \decision{Should the plugin intervene when saving, connecting or executing?}
    {SaveChanges, connection, command and transaction interceptors, update pipeline
    (page~\pageref{sec:decide-runtime})}
  \decision{Is it about schema changes, snapshots, compiled models or scaffolding?}
    {Migrations and design-time services (page~\pageref{sec:decide-tooling})}
  \decisionend{No intervention in EF needed: a helper method or code in the application
    (level~1 from chapter~\ref{ch:what-is-an-ef-core}).}
\end{decisiontree}

Each row of the area tables describes a problem, the mechanism for it, the simpler
alternative to check first, and the typical wrong choice. Below the mechanism, its
properties are shown in grey:

\begin{datatable}{H{0.55}H{1.45}}
  \textbf{Label} & \textbf{Meaning} \\
  \tablehead
  public & Gets by with EF Core's public API. \\
  \tablerule
  provider base & Derives from the provider's implementation. Ties the plugin to that
  provider; with Npgsql, the base classes or their dependencies usually live in
  \code{.Internal} namespaces (EF1001). \\
  \tablerule
  pubternal & Even EF's own type lives in an \code{.Internal} namespace. \\
  \tablerule
  multiple, single & Cardinality according to EF Core 10's service tables
  (appendix~\ref{app:A}). \\
  \tablerule
  no service & Works through the model or the options, not through the internal service

  \tablerule
  Singleton, Scoped & Lifetime in the internal provider; with “design time” in the service

\end{datatable}

\section{Configuration and services}\phantomsection\label{sec:decide-configuration}

Every level~3 plugin starts with an options extension. The actual decision is made for each
individual service: how does it get into the internal provider? The tree follows the order
from “Extend or replace?” (chapter~\ref{ch:ef-core-s-architecture-from}):

\begin{decisiontree}
  \decision{Is there a plugin interface or an interceptor for the purpose?}
    {\code{Try\allowbreak{}Add} through the services builder or
    \code{Add\allowbreak{}Interceptors}: multiple, composable}
  \decision{Is it a service of your own that EF does not know?}
    {\code{Try\allowbreak{}Add\allowbreak{}Provider\allowbreak{}Specific\allowbreak{}Services};
    choose the lifetime yourself}
  \decision{Does the public interface of the single service suffice to extend the result?}
    {Decorate: wrap the existing registration and keep its lifetime}
  \decisionend{Replace with \code{Replace}: derive from the provider's class, offer the logic
    as public and virtual, document the replacement.}
\end{decisiontree}

  \textbf{Problem and mechanism} & \textbf{Check first} & \textbf{Typical wrong choice} &
  \textbf{Ch.} \\
  \tablehead
  \textbf{The plugin should be switched on and configured.}
  \code{IDb\allowbreak{}Context\allowbreak{}Options\allowbreak{}Extension},
  \code{Use} method, options builder
  \cellmeta{public · no service, part of the options} &

  \ref{ch:the-options-extension}, \ref{ch:public-api-and-integration-into} \\
  \tablerule
  \textbf{A singleton service needs the settings.}

  \cellmeta{public · multiple · Singleton} &
  Scoped services can inject \code{IDb\allowbreak{}Context\allowbreak{}Options} directly. &

  \ref{ch:registering-services} \\
  \tablerule
  \textbf{The plugin brings services of its own.} \code{Apply\allowbreak{}Services} with

\section{Model, types and values}\phantomsection\label{sec:decide-model}

Everything in this area is decided during model building, that is once per internal
provider and context type, and ends up in the cached model. Value converters and value
generators do run on every read, write or add, but as the model has configured them.
Run-time values therefore have no place in this configuration.

\section{Queries}\phantomsection\label{sec:decide-queries}

At which stage of the pipeline a desired change sits is shown by the map in
chapter~\ref{ch:the-query-pipeline}; this section then chooses the mechanism. Most query
extensions run once per query shape, and the result is cached. Values that change per
execution therefore belong in the SQL as a parameter or database function, never as a
constant. The following tree is
ordered by increasing depth of intervention; one question concerns every custom function
and therefore comes first:

\begin{important}[Methods without data reference]
  If a custom method has no argument that refers to a column
  (\code{Current\allowbreak{}Tenant(\allowbreak{})}, session or time functions), it needs an
  \code{IEvaluatable\allowbreak{}Expression\allowbreak{}Filter\allowbreak{}Plugin} in
  addition to the translator. Otherwise EF evaluates it in .NET beforehand.
\end{important}

\begin{decisiontree}
  \decision{Does only one application need a database function in LINQ?}
    {\code{Has\allowbreak{}Db\allowbreak{}Function} or \code{[Db\allowbreak{}Function]} in
    the application's model; no plugin}
  \decision{Should a method call become an SQL function?}
    {\code{EF.\allowbreak{}Functions} method and
    \code{IMethod\allowbreak{}Call\allowbreak{}Translator\allowbreak{}Plugin}}
  \decision{Should a property or field be translated?}
    {\code{IMember\allowbreak{}Translator\allowbreak{}Plugin}}
  \decision{Should values be aggregated over several rows (\code{Group\allowbreak{}By})?}
    {\code{IAggregate\allowbreak{}Method\allowbreak{}Call\allowbreak{}Translator\allowbreak{}Plugin}}
  \decision{Is the SQL syntax not a function call, or do the NULL semantics differ?}
    {Custom \code{Sql\allowbreak{}Expression}, SQL generator and nullability processor:
    replace two single services}
  \decision{Should the LINQ tree be rewritten before translation?}
    {\code{IQuery\allowbreak{}Expression\allowbreak{}Interceptor}}
  \decision{Should the loaded object be created, completed or checked?}
    {\code{IMaterialization\allowbreak{}Interceptor}}
  \decisionend{Last resort: adjust the translated tree via
    \code{IQuery\allowbreak{}Translation\allowbreak{}Postprocessor\allowbreak{}Factory}
    (single service, provider base).}
\end{decisiontree}

  \textbf{Problem and mechanism} & \textbf{Check first} & \textbf{Typical wrong choice} &
  \textbf{Ch.} \\
  \tablehead

  \code{IMethod\allowbreak{}Call\allowbreak{}Translator\allowbreak{}Plugin}

\code{IDesign\allowbreak{}Time\allowbreak{}Services}, not in
\code{Apply\allowbreak{}Services}.

  The declarative way through annotations, almost always the better choice. &
  Replacing the differ just because a changed annotation needs SQL; the SQL generator does
  that. &
  \ref{ch:custom-migration-operations} \\
  \tablerule
  \textbf{Snapshots should show Fluent API instead of \code{Has\allowbreak{}Annotation}.}
  \code{IAnnotation\allowbreak{}Code\allowbreak{}Generator}, loaded through
  \code{IDesign\allowbreak{}Time\allowbreak{}Services} and
  \code{Design\allowbreak{}Time\allowbreak{}Services\allowbreak{}Reference}
  \cellmeta{provider base · single · Singleton (design time)} &
  Do nothing: \code{Has\allowbreak{}Annotation} in the snapshot works, it is just hard to

  internal provider; not removing translated annotations from the dictionary. &
  \ref{ch:design-time-services} \\
  \tablerule
  \textbf{The compiled model should omit design-time annotations or contain complex

\begin{important}[Four wrong choices that occur in every area]
  \textbf{Replacing where a plugin interface or a decorator suffices.} Every replacement
  excludes another plugin (chapter~\ref{ch:registering-services}).

  \textbf{Storing run-time values where EF caches.} The options hash, the model and
  translated queries are reused. Per-request values belong in parameters, in the database
  session or in interceptors from the application.

  \textbf{Mistaking a run-time hook for a guarantee.} Interceptors only see what goes
  through EF (chapter~\ref{ch:bulk-operations-and-the-limits}).

  \textbf{Confusing design time and run time.} Design-time services do not belong in the
  internal provider, design-time annotations not in the runtime or compiled model.
\end{important}
